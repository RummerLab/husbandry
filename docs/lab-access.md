# Shared lab access gate

This PR implements a standard HTTP Basic gate in SvelteKit's server hook, using the maintained `basic-auth` parser and Node's fixed-size timing-safe comparison. It protects server-rendered pages and APIs (including direct submission POSTs) across every hostname reaching the application. Credentials are server environment variables; nothing is embedded in browser JavaScript. This is an interim **shared lab credential**, not individual researcher attribution. Keep initials; individual approved accounts/institutional SSO are the next step when per-person revocation is needed.

## Activate only after configuring the deployment

`LAB_ACCESS_ENABLED` defaults to `false`: this PR can be merged while access setup is still pending without locking out existing lab workflows. The website remains public in this state. To activate, configure and distribute credentials, enforce the rate rules, verify a preview, and explicitly set `LAB_ACCESS_ENABLED=true`. This is not active access protection until that switch is enabled.

Set `LAB_ACCESS_USERNAME` (default `lab`) and a random `LAB_ACCESS_PASSWORD` of at least 24 characters in each protected Vercel environment. Store/distribute it through the lab's password manager, never Git, URLs, analytics or a public QR code. Configure the `husbandry-login` SDK rate rule and submission rules as described in [rate limiting](rate-limiting.md). Check all production/custom/deployment URLs and previews with the test procedure below. Once enabled, missing or invalid credentials, or RATE_LIMIT_MODE other than enforce, fail closed with 503 on Vercel or NODE_ENV=production. Off mode is for rollout; an enabled gate always requires credentials. Do not activate until the lab administrator has distributed access and rehearsed queue recovery.

Browsers prompt for HTTP Basic credentials on page navigation; no lab member needs a Vercel developer account. HTTPS is mandatory in deployed environments. The browser retains credentials for the authentication realm; there is no custom session JWT or cookie to forge. Cookies are not used for authentication. Mutating authenticated requests also require an exact same-origin Origin header; direct scripts must supply valid Basic credentials and the intended origin.

APIs return 401 JSON without a browser challenge/redirect. An expired/rotated password pauses submission replay indefinitely while preserving payloads. In device history, select **Sign in again to resume sync** to navigate to `/login`, where the browser prompts for the updated credential. After authentication the app verifies `/api/access` over the network before clearing the auth pause. Offline cached shells cannot authorize writes. Manual Sync/reconnect cannot remove rate-limit cooldowns. If a browser keeps resending an old credential, close that browser session and reopen; browser HTTP-auth caches do not offer reliable application logout.

## Scope and privacy

Public resources are static build/assets, icons, service worker and minimal `/api/health`; they contain no submitted history or secrets. `/api/health/diagnostics` requires its separate bearer token, since Basic and Bearer share the Authorization header. Protected responses are private/no-store in HTTP caches. The service worker deliberately retains the previously authorized app shell for offline work, and local records remain on that device. `/login`, API calls, errors and challenges are never cached as shells. The access gate cannot erase offline caches or provide privacy between people sharing one browser profile; protect lab devices accordingly. Google Sheet sharing permissions remain a separate boundary.

## Rotation, recovery and verification

The lab administrator owns credential distribution/rotation. Change the server password and redeploy; old credentials cease authorizing requests. Removing a person from a shared-password group requires rotation for everyone. Preserve pending records and authenticate with the new password; do not clear browser storage. Recovery is through a Vercel project administrator restoring the environment values and redeploying, not a public bypass URL.

Test on preview before production: unauthenticated and invalid-password direct POSTs produce zero Sheets calls; correct credentials + same origin succeed; cross-origin writes fail; missing config fails closed; rotation causes a paused queue; reconnect after sign-in syncs once using existing receipt IDs. Verify every hostname and observe login rate limits. Use a disposable workbook for live writes. The PR does not alter live secrets or platform protection. Vercel Password Protection is an alternative if the team prefers a platform gate and accepts its plan cost; do not enable it in addition without testing dual prompts and PWA behavior.
