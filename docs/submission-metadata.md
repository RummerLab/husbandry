# Spreadsheet provenance migration

New submissions capture the existing browser installation ID at initial durable queue creation. Both submission paths use that queue helper. Already queued payloads are never enriched or rewritten; missing legacy IDs stay unknown. A browser ID can reset or be spoofed and is not a user identity or an authorization key. Do not send it to analytics. All local history remains per-device.

Metadata export is deliberately **off by default**. Set `GOOGLE_SHEET_METADATA_ENABLED=true` only after migration and preview verification. With it off, existing row widths remain exactly 21/21/84/23. When enabled, every new operational row has four trailing columns: Submission ID, Client Device ID, Client Submitted At (UTC), Server Received At (UTC). Totals become 25/25/88/27; every existing operational column stays in place, including the Notes and quantity columns. A full routine shares one Submission ID, device ID and first successful server-received timestamp across its four rows. Server Received At is an ingestion timestamp, not proof of when an observation occurred. The client timestamp is untrusted.

## Runbook (lab administrator)

1. Back up the workbook and inventory downstream formulas, exports and integrations. This is an explicit schema extension: the historic Excel contract applies to the operational prefix, not to the four new metadata columns. Update consumers and AGENTS.md documentation together. Keep the existing `husbandry_*` named ranges intact.
2. Create a disposable workbook copy, configure its ID/credentials in a private environment file, and run `node --env-file=.env scripts/migrate-sheet-metadata.mjs`. The default is a read-only dry run. It requires all operational headers and refuses unfamiliar occupied trailing header cells. The script also checks proposed metadata columns below blank headers, including formula text, and refuses occupied cells before writing. Review formatting and downstream dependencies manually as well; historical data is never overwritten.
3. On the disposable copy only, use `--apply`. One atomic batch extends column capacity if needed and writes the four headers on all operational tabs. It never backfills, reorders or clears existing records. Repeating a completed migration is a no-op. Restore the backup if the lab rejects the schema extension; keep metadata export disabled until the schema is agreed.
4. Enable metadata export in preview using the copied workbook. Test single/four-module rows, legacy queues without IDs, concurrent replay, lost acknowledgements and numeric-looking notes. Metadata and operational rows must commit with the deduplication receipt in one atomic batch. Missing/misplaced headers block new writes instead of silently placing metadata in operational fields.
5. Arrange a maintenance window for production migration, drain/reconcile pending legacy records as appropriate, apply the reviewed schema, then enable the flag and deploy. Keep old rows' provenance blank/unknown; it cannot be safely reconstructed. Existing acknowledged receipts remain valid and are not rewritten or retroactively annotated. Check the first new rows and downstream consumers before ending the window.

A retry returns the existing receipt and does not change Server Received At. Received time is server-generated outside the client receipt hash. Never change the contents of an acknowledged submission or replay an existing ID with new metadata. To disable export, set the flag false and redeploy; retain the appended headers/history, and new metadata cells will be blank. Removing columns is a separate reviewed operation.

The implementation and tests do not modify the production workbook. Do not mark rollout complete until a disposable-workbook rehearsal and production checks have been performed by the lab administrator.
